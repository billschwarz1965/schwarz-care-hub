Country-specific L1 navigation

The three architecture options differ in what sits above the local instance. This page covers a different axis: how the L1 navigation inside a local instance varies by country. Some markets need a top-level section that does not exist anywhere else — the US needs Medical Value & Outcomes, which serves payors rather than treating clinicians.

The rule this implies: L1 is not a single global list with translations. It is a shared core set plus a per-market extension set. A market can add an L1 the core does not have; it should not be able to silently rename or reorder the core, or cross-market navigation and analytics stop comparing.

The US case: Medical Value & Outcomes

US-ONLY L1 · MVO

Medical Value & Outcomes

A top-level section for the audiences that decide access rather than prescribe: payors at insurance companies, hospitals and government. It is not a therapeutic-area page and does not belong under one — its organising principle is the decision being supported, not the disease.

medical.campus.sanofi/en-us/medical-value-outcomes

WHO IT SERVES

  • Payors at insurance companies
  • Hospitals and health systems
  • Government bodies

SCOPE IN THE US

  • Specialty Care
  • General Medicines
  • Spans both GBUs — so it cannot sit inside either

That last point is the structural consequence. Because MVO covers Specialty Care and General Medicines, it cannot be nested under a GBU or a therapeutic area without duplicating it. It has to be a sibling of the TA set at L1, which is exactly why "different L1 links per country" is the requirement rather than "different content under the same L1".

How it interacts with the three options

OptionEffect on a market-specific L1
Option 1 — global portal, flat sections Works. The global root keeps its flat TA sections; /en-us adds MVO to its own L1 set. Risk: a visitor at the global root sees no MVO entry point, so US payors must land in the locale directly.
Option 2 — global portal, TA-nested Works, with the most friction. Option 2's organising promise is "TA is always the layer", and MVO is deliberately not a TA. It becomes the visible exception to the pattern.
Option 3 — no global portal Cleanest fit. Every market already defines its own instance, so a per-market L1 set is the native model rather than an exception.

What has to be defined to build it

The mechanism is a per-locale L1 manifest: a shared core plus an ordered extension list.

// one entry per locale; core is inherited, extensions are additive
core: [ Therapeutic Areas, Programs, Events, Resources, About Medical ]
approval: [ gtmc, medical-product-line-owner ]   // both required, any L1 change

en-us:
  extends: core
  add:
    - id: medical-value-outcomes
      label: "Medical Value & Outcomes"
      audience: [ payor, hospital, government ]
      gbu: [ specialty-care, general-medicines ]
      gated: true          // payor audience, not HCP self-attestation
      position: after:therapeutic-areas

en-gb, fr-fr, de-de:
  extends: core           // no extensions defined yet
DECIDED · L1 APPROVAL

Adding, removing or renaming an L1 section requires approval from GTMC and the Medical Product Line owner. Both, not either — GTMC holds the cross-market consistency of the core set, the Product Line owner holds the platform. This is what stops a market adding L1s unilaterally while still leaving a route for a genuine case like MVO.

That resolves governance. Three decisions remain, none of which are design questions:

DecisionWhy it matters
Gating modelMVO's audience is not HCPs. The existing HCP self-attestation gate is the wrong check for a payor, and may be the wrong legal basis. See the section below.
Analytics comparabilityCross-market reporting breaks silently when L1 sets diverge unless market-specific sections are tagged as extensions.
Ownership across GBUsMVO spans Specialty Care and General Medicines, so it needs a single content owner who sits above both — separate from the GTMC / Product Line approval of the L1 itself.

Gating model — deferred attestation

PROPOSED · NOT YET CLEARED WITH LEGAL & REGULATORY

HCPs land on an ungated home page with no initial attestation, on the condition that everything on it is proactive approved content. Attestation is deferred until the user clicks the first piece of content or link that actually requires it. Main pages stay ungated.

Rationale: too many attestations create a bad user experience. Today the gate is charged at the door, before the visitor has any reason to accept it.

The attestation moves from a front door to a threshold inside the site:

UngatedHome & main pagesProactive approved content only. Crawlable, linkable, citable.
→
UngatedBrowse & searchTitles, summaries, structured data.
→
Attest hereFirst gated assetTriggered by the click, in context, once the value is already visible.
→
CarriedEverything afterOne attestation persists for the session.

Two independent bodies of evidence already point here

FindingSource
"Use authentication to unlock depth, not basic information" — HCPs "want tailored formats without exchanging their personal details" frog / Capgemini Invent Content Experience research, July 2026 — 12 HCP interviews, US / France / Germany
"No mandatory registration to begin; value delivered before commitment." NP and KOL modes abandon an experience that does not deliver value inside two minutes MedVerse User Personas & Journeys, April 2026
Gated content is invisible to AI-mediated discovery. Zero-click search rose 56% → 69%; being citable now matters more than being visited Sanofi SEO & GEO 2025, October 2025

So this is not only a UX preference. An ungated surface is also the only version of the site that AI systems can read, which is the same conclusion the discovery evidence reaches from the opposite direction.

What Legal & Regulatory need to rule on

QuestionWhy it is not obvious
Is an ungated page a proactive communication? In most frameworks an openly accessible page is proactive by definition, which constrains it to approved proactive content and excludes anything reactive or off-label. That is the condition this model depends on, so it needs confirming rather than assuming.
Can "HCP-only" content sit behind a click rather than a door? Some markets treat HCP-only material as requiring verification before any exposure, including titles and summaries in navigation or search results.
Does attestation persist, and for how long? A single per-session attestation is the whole UX benefit. Per-asset attestation returns to the current experience.
Does this vary by market? Very likely. If some markets require a front-door gate, the model becomes a per-locale setting alongside the L1 manifest above.
What gate applies to a non-HCP audience? MVO serves payors, hospitals and government. HCP self-attestation is the wrong question to ask them, so the gate has to be audience-aware, not a single global check.
Status: proposal only. Nothing here should be treated as cleared. The dependency is explicit — the model holds if and only if the ungated surface can be constrained to proactive approved content, and that is a Legal and Regulatory determination, not a design one.
