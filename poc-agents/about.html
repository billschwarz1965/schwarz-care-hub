About the MedVerse Agent Ecosystem

A standalone explorer for the agent architecture behind MedVerse — the agents, the intelligence hubs they draw on, and the governance layer every output passes through.

What This Build Is

This edition ships one module: the Agent Ecosystem. It is an architecture explorer, not a concierge — there is no chat assistant answering clinical questions here, and no patient- or HCP-facing workflow. What it does provide is a walkable map of how MedVerse is built and governed, with a runnable demo for most agents so you can see the full path from a user's question to a compliance-checked answer.

Use it to answer architecture questions: which agents exist, what each one does, which data it depends on, which governance agents supervise it, and what a real interaction looks like end to end.

What You Can Do Here

  • Walk the four-layer architecture — click any layer to expand its agents
  • Browse the full agent inventory with users, hub dependencies, and governance pairings
  • Run an agent demo — input, processing, draft output, governance review, verified result
  • Inspect each intelligence hub: its data sources, capabilities, and dependent agents
  • Open any governance agent to see which business agents it supervises
  • Ask the Ecosystem AI about architecture, agent counts, personas, or governance
  • Search live ClinicalTrials.gov data from the trial intelligence panel

The Four Layers

Every MedVerse agent sits in one of four layers. A user request enters at the top, is served by an orchestration agent, which composes intelligence from the hubs below, and is validated by the governance layer before anything is returned.

1 — User Experience Layer

The audiences MedVerse serves. Each gets a purpose-built experience powered by the agents below.

2 — Agent Orchestration Layer

Business agents that own a workflow: pre-call briefings, trial matching, disease navigation, literature scouting.

3 — Intelligence Hub Layer

Foundational knowledge graphs. Agents query a hub rather than holding their own copy of the truth.

4 — Governance Layer

Compliance agents that review every output before delivery. Non-optional and non-bypassable.

Compliance by Design

Governance is not a review step bolted on at the end — each business agent is paired with named governance agents at design time, and those pairings are part of the agent's specification. The demos show this working: a draft is produced, the governance layer inspects it, and corrections are applied before the output is delivered. Some demos deliberately show a correction being made rather than a clean pass.

Every interaction produces an audit record — who asked, what was generated, which checks ran, and what changed. That record is what makes the platform inspectable after the fact.

Enterprise Data & Scaling

Agents are defined declaratively — an agent is a specification (identity, users, hub dependencies, governance partners, status) rather than bespoke code. Adding an agent means adding a specification and pointing it at the hubs it needs; the ecosystem view, persona filters, architecture counts, and governance mappings all derive from that definition automatically.

Each agent in this build has a written specification in docs/agents/ covering its purpose, inputs, data dependencies, processing steps, outputs, governance pairings, and the enterprise data it would bind to in production — so an agent can be recreated or extended without reverse-engineering the demo.

Part of a Wider Platform

The Agent Ecosystem is one module of MedVerse. The full platform also includes concierge experiences for healthcare professionals, patients and caregivers, medical science liaisons, and medical affairs teams, plus dedicated intelligence modules for disease state navigation, literature, and medical congresses. Those modules are not part of this build — the agents you can browse here are the ones that power them.
